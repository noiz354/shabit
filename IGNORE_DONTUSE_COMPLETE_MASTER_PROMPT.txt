
## ⚡ TL;DR — 5 Gap Paling Berbahaya yang Terlewat di Ronde 1

1. **Tidak ada sistem notifikasi** → habit tracker tanpa reminder = dead app
2. **Tidak ada UU PDP consent flow** → app bisa ditolak Play Store / App Store Indonesia
3. **Plaid/Nordigen tidak ada di Indonesia** → AI akan mengarang flow OAuth yang fiktif

5. **Aksesibilitas disebut di audit tapi tidak pernah masuk prompt** → gap antara "tahu" dan "melakukan"

Dengan 9 prompt ini, kamu punya coverage **end-to-end yang sebenarnya**: dari pertama user dengar app → install → daily use → retention → compliance → developer handoff. 🚀

## 🔄 Revisi Urutan Eksekusi (Koreksi Kritis Ronde 2)

Ronde 2 menempatkan Design System (P9) di **akhir**. Ini **salah secara praktis**. Developer yang menerima wireframe tanpa design system akan mengarang warna, spacing, dan typography sendiri — lalu design system jadi retrofit yang tidak konsisten.

**Urutan yang benar:**

```
Fase 0: FOUNDATION (kerjakan paralel, sebelum wireframe)
  ├── Prompt 2  (IA + Navigasi + MVP Phasing)
  ├── Prompt 9  (Design System Baseline) ← PINDAH KE SINI
  └── Prompt 10 (Event Tracking Plan)    ← PINDAH KE SINI

Fase 1: CORE EXPERIENCE (berurutan)
  ├── Prompt 1  (Journey Map) ← validasi IA
  ├── Prompt 11 (Progressive Onboarding) ← BARU, sebelum wireframe detail
  ├── Prompt 3  (Auth + Consent + Permissions)
  ├── Prompt 4  (Habit Tracker)
  └── Prompt 5  (Money Tracker)

Fase 2: DIFFERENTIATOR & RETENTION
  ├── Prompt 6  (Cross-Feature Synergy)
  ├── Prompt 7  (Notifikasi & Re-engagement)
  └── Prompt 12 (Growth & Sharing) ← BARU

Fase 3: COMPLIANCE & POLISH
  └── Prompt 8  (Settings, Privacy, Subscription, Legal)
```

**Mengapa Design System di Fase 0?**
- Wireframe Prompt 4-8 akan menyebut "progress ring hijau", "error merah", "spacing md" — semua istilah ini harus sudah terdefinisi di Prompt 9.
- Jika P9 di akhir, AI di Prompt 4 akan mengarang warna `#4ADE80` dan AI di Prompt 5 akan mengarang `#22C55E` untuk hal yang sama. Inkonsisten.

**Mengapa Event Tracking di Fase 0?**
- Setiap wireframe di Fase 1-2 harus mencantumkan event name di setiap interaksi kunci. Tanpa tracking plan di awal, event name akan tidak konsisten antar-prompt.

## 📋 Prompt Chaining Protocol (Meta-Layer Baru)

Ini yang **sama sekali tidak ada** di Ronde 1 dan 2, tapi kritis agar output 12 prompt tidak bertabrakan:

```

1. OUTPUT PROMPT 2 (IA) adalah "single source of truth" untuk

   - Nama komponen: kebab-case (progress-ring, bottom-sheet)

6. VERSI: Setiap output prompt harus di-header dengan:
```

## ⚡ TL;DR — 5 Gap Paling Berbahaya yang Terlewat di Ronde 2

1. **Design System di urutan terakhir** → wireframe sudah terlanjur pakai warna/spacing sembarangan, design system jadi retrofit yang tidak konsisten. **Fix: pindah ke Fase 0.**

2. **Tidak ada monetisasi & paywall** → AI mengarang model bisnis sendiri; IA tidak punya modul Subscription; developer tidak tahu fitur mana yang di-gate. **Fix: Patch P2 + P8 + Prompt baru.**

3. **Tidak ada app permissions timing** → minta Health + Notification + Biometric di Day 1 = user deny semua = fitur mati = App Store rejection. **Fix: Patch P3 dengan permission primer bertahap.**

4. **Tidak ada event tracking plan** → tim data buta, product decision berbasis gut feeling, tidak bisa ukur apakah Saving Streak benar-benar meningkatkan retensi. **Fix: Prompt 10 baru di Fase 0.**

5. **Tidak ada progressive onboarding** → semua fitur di-expose di Day 1 = cognitive overload = 77% churn di minggu pertama. **Fix: Prompt 11 baru dengan matriks Day 1/7/30.**

# 🔬 Audit End-to-End Ronde 4 — *Final Consolidation & The Missing Layer*

---

## Pengantar: Mengapa Ronde 4 Masih Diperlukan

Ronde 3 sudah mengidentifikasi 45 gap dan menghasilkan 12 prompt. Secara **konten UX**, itu sudah sangat komprehensif. Tapi setelah saya simulasikan skenario nyata — *"PM junior membuka dokumen ini dan mencoba menjalankannya Senin pagi"* — ada **satu masalah struktural raksasa** yang membuat semua ronde sebelumnya tidak bisa langsung dieksekusi:

> **Tidak ada satu pun prompt yang "clean".** Setiap prompt sekarang terdiri dari versi asli + 2-3 lapisan patch yang tersebar di 3 dokumen berbeda. PM harus melakukan *manual merge* 50+ instruksi patch ke dalam 12 prompt sebelum bisa di-copy-paste ke AI. Ini bukan end-to-end — ini *end-to-confusion*.

Selain itu, ada **3 lapisan yang sama sekali belum tersentuh** di semua ronde:

1. **Data model / entity schema** — AI tahu "habit" dan "transaction" sebagai konsep UI, tapi tidak tahu struktur datanya. Developer akan membuat schema yang tidak cocok dengan wireframe.
2. **QA acceptance criteria** — Tidak ada cara untuk memverifikasi apakah output AI "benar". PM tidak tahu kapan harus accept vs iterate.
3. **System prompt wrapper** — Tidak ada instruksi global yang memberi AI konteks lintas-prompt, sehingga setiap prompt berjalan di "ruang hampa".

#### Prompt 13 — Data Model & Entity Schema

```

Konteks:

HabitWealth. Untuk setiap entitas, sertakan:

  Per entitas, gunakan tabel:
  | Field | Tipe | Required | Default | PII? | Keterangan |

  Account 1──* Transaction
  ...
```

## 🏁 Pernyataan Penutup Ronde 4

Setelah 4 ronde audit, 55 gap teridentifikasi, dan 15 prompt + 1 system prompt + 3 checkpoint + execution playbook:

**Apakah ini sudah 100% end-to-end?**

Jujur: **95%**. Sisa 5% yang tidak bisa di-cover oleh prompt UX adalah:

- **Product strategy** — Apakah HabitWealth harus ada? Apakah market-nya cukup besar? Ini ranah founder, bukan prompt.
- **Engineering architecture** — Microservice vs monolith? Firebase vs AWS? Ini ranah CTO.
- **Legal review final** — UU PDP interpretation, OJK licensing untuk open banking. Ini ranah lawyer.
- **User testing nyata** — Prompt menghasilkan *hipotesis* desain. Validasi sesungguhnya hanya bisa dari usability testing dengan manusia nyata.
- **Post-launch iteration** — Prompt ini berhenti di Day 1 launch. Setelah itu, data analytics (P10) yang harus men-drive iterasi.

Tapi untuk **scope UX design prompt yang bisa di-copy-paste ke AI dan menghasilkan output yang langsung bisa di-review oleh tim produk** — ini sudah se-end-to-end yang bisa dicapai. 🎯
